# Editorial standard for the `Uni*` documentation

What a library must document, how it is arranged, and what each surface refuses
to contain. Applies to every `Uni*` repository.

This is a standard to measure against, not a template to fill. Where it states
a number, the number came from somewhere and the source is named.

---

## 1. Three surfaces, and one rule about their boundary

| Surface | What it is | Read how |
|---|---|---|
| **The book** — `book/`, nimibook | Narrative. Teaches the domain. | Front to back |
| **The reference** — `pages/api/`, generated by `nim doc` | Every public item. | Consulted, never read |
| **The README** | What this is, whether you want it, how to start. | Skimmed in thirty seconds |

**Each is defined by what it refuses.** The refused material always has a named
destination — that is the whole of the discipline, and it is Django's, whose
contributing guide defines every content type by what it must not hold.

- The **book** refuses exhaustive signatures. → the reference.
- The **reference** refuses narrative and choice guidance. → the book.
- The **README** refuses everything it can link to.

**Linking is asymmetric.** The book links into the reference at every point of
insufficiency, as often as needed. The reference links back to the book **only
from module roots**, never from an item. A reader who arrived at one function
mid-task must not be dropped into a reading path.

**One example universe per library.** Define the worked example once, in the
book, and have the reference and the README reuse it by reference rather than
inventing their own. Django does this literally; it is why its query guide and
its QuerySet reference read as one work.

### What we do *not* do

We do not give books a four-part `tutorial / how-to / reference / explanation`
structure. Diátaxis — the framework those names come from — says of exactly
that: *"It certainly does not mean that you should create empty structures for
tutorials/howto guides/reference/explanation with nothing in them. Don't do
that. It's horrible."* ([diataxis.fr](https://diataxis.fr/how-to-use-diataxis/),
read 2026-08-26.) Its own site does not use those categories as containers.

**Chapters are named after the domain, not after a content type.** `BigInt`,
`Fixed`, `Rational`, `Interval` — not `Tutorial`, `Concepts`, `Guide`.

## 2. What every library must have, and what it adds as it grows

Do not normalise the books to a common length. Normalise them to a common
ladder: the same sections, in the same order, with the higher rungs simply
absent from the smaller libraries.

**The predictor of how much documentation a library needs is not its size. It
is the number of decisions a reader must make before calling anything.**
UniChecksum: one — which family. UniMath: many.

### Rung 1 — the floor, for every library without exception

1. Name and a one-sentence statement of the problem it solves.
2. Installation, for each of the three surfaces (Nim, C, Python).
3. A runnable example.
4. **That example, explained.** Unexplained examples are a distinct, measured
   failure, not a stylistic quibble.
5. **A rendered, browsable reference for every public item, on all three
   surfaces.** Comments in a header satisfy nothing until they are rendered
   somewhere a reader can browse — the OpenSSF best-practices criterion is
   explicit about this, and it also says generating them is the right way.
6. Failure semantics per routine: preconditions, what raises in Nim, what the C
   ABI clamps, what the Python binding turns into an exception.
7. Which versions and platforms are supported.
8. The licence.
9. Where to ask, and whether contributions are accepted.

### Rung 2 — when the reader must choose before calling anything

A capability matrix or feature list; the numeric guarantees (rounding,
overflow, exactness).

### Rung 3 — when there is more than one correct way to use it

Task-shaped recipes, one per scenario, kept apart rather than tangled into the
narrative; a short "why this one rather than that one".

### Rung 4 — when there is an internal model the reader must hold

The high-level design and why it is that way. Readers report needing this to
use an API properly; it is not decoration.

### Rung 5 — when one reader will not read the whole thing

The chapter split, a table of contents, a changelog with breaking changes
flagged, the security expectations.

### On length

**Do not shorten a book to make it better.** In the largest study we found on
what developers actually complain about (Uddin & Robillard, *IEEE Software*
2015, 323 professionals), incompleteness was reported by 20 developers and
bloat by 11 — and bloat ranked lowest of ten problems in both severity and
frequency. Cutting trades the least severe problem for the most severe one.

What the complaint records as "bloat" is **length without an orienting
overview**, not length. The fix is a purpose statement at the top.

A 425-word book for a perceptual colour engine is at more risk than a
3,400-word one for arbitrary-precision arithmetic.

## 3. What a chapter contains

Ten slots, in this order. Lower rungs omit slots; nobody reorders them.

1. **Title** — the domain noun. No verb, no subtitle after a colon.
2. **Definition, then orientation.** One sentence defining the thing. Then what
   this chapter gets you, what it assumes, and what it does not cover.
   *The definition comes first, before the motivation.* Every chapter of the
   Rust book we examined opens on a definition, not on a problem.
3. **Motivation** — either a short when-to-use list, or the painful version
   first and the good one after.
4. **Prerequisite background, set apart.** A blockquote or an explicit backward
   link. Never inline: required-but-tangential material must not interrupt the
   spine.
5. **Numbered, captioned listings, smallest first — including at least one that
   deliberately fails**, with the real output pasted. For us that means showing
   an actual `PreConditionDefect`, an actual clamp, an actual `ValueError`.
   This is the single most distinctive teaching device in the sources surveyed,
   and our contracts make it nearly free.
6. **The API surface for this chapter**, linked per item into the generated
   reference. Never retyped: a paraphrased signature is a signature that will
   drift.
7. **Failure and edge behaviour**, as a named section. The three-surface
   difference belongs here: *raises* in Nim, *clamps* in C, *raises* again in
   Python.
8. **Where the surfaces differ in meaning**, not merely in syntax.
9. **References** — primary sources, with section and page where they exist.
10. **Next — at most five links.** That cap is Kubernetes' published limit and
    the only quantitative one we found.

Close on a forward pointer that names the deficiency the next chapter fixes.

## 4. Rules the tooling imposes

These are not style. Breaking them produces broken pages.

- **Never use footnotes.** nimibook's markdown does not merely ignore them, it
  renders corrupted HTML with no error: `text[^1]` becomes a link to `the`.
- Also unavailable, and silently: task lists, bare autolinks, definition lists.
- **The first chapter must be named `index`**, or the site root answers 404.
- **A `.nim` chapter must call `nbInit(theme = useNimibook)`.** A `.md` chapter
  gets the theme automatically; a `.nim` one is compiled and run standalone and
  renders unthemed without it.
- **A `.md` chapter cannot execute anything.** Everything runnable is `.nim`.
- **Never `echo` a `<` followed by a letter.** nimib interpolates code output
  into the page without escaping it, so the browser eats it as a tag.
- **Headings have no anchors.** Do not write a cross-chapter link to a section
  until the theme supplies them; it will land silently at the top of the page.
- **`nimib.toml` ignores keys it does not know**, without warning. Only the
  nine documented fields reach the build.

## 5. What is checked, rather than trusted

A standard nothing verifies is a preference. These are gates:

| Check | Where |
|---|---|
| Every code block in the book compiles and runs | nimibook, at build |
| The notebook's committed outputs match what the code produces | shared CI |
| Every public symbol carries a doc comment | *to build* |
| Every claimed value in the prose is produced, not typed | *to build* |
| Every link resolves | *to build* |
| Contrast of every text token, both modes | `lituus-theme/tools/contrast.py` |

The last three do not exist yet. Until they do, the claims they would check are
the ones to distrust first.

## 6. Voice

English. Terse. Say what is done and why, not what could be done.

The book may address the reader; the reference may not. That split tracks the
reading contract: a book is read front to back, a reference page is arrived at
from a search with no preamble.

State the reading contract in the first paragraph of the book. Rust's — *"this
book assumes that you're reading it in sequence from front to back"* — is the
model.

**Publish the gaps.** A section naming what is not covered, not verified, or
not yet ported is worth more than its absence. The best algorithm references we
found all do this, and one grades the strength of its own evidence.
